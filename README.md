# Local LLM Gateway

A local-first LLM gateway built with **TypeScript, Fastify, Ollama, Redis, Prometheus, and Docker**.

This project runs an open-weight LLM locally on an Apple Silicon Mac and places a backend service in front of it. The gateway adds API-key authentication, rate limiting, bounded concurrency, queueing/backpressure, request cancellation, streaming, and Prometheus metrics.

The current implementation uses **Ollama + `llama3.2:3b`**. The design is intentionally OpenAI-compatible so the same client contract can later point to other models or providers.

---

## 1. What this project actually does

The simplest way to understand the project is:

```text
Client (curl / Postman / application)
            |
            v
     Fastify Gateway :3000
            |
     +------+------+----------------+
     |      |      |                |
    Auth  Rate   Queue          Validation
         Limit  / Semaphore
            |
            v
       Ollama :11434
            |
            v
      Llama 3.2 3B
            |
            v
      Apple M4 GPU
```

Ollama is the **local model server**. The Fastify application is the **gateway you built around the model**.

That distinction matters:

```text
ollama run llama3.2:3b
```

means:

> I want to use the model.

Whereas:

```text
POST /v1/chat/completions
```

through this project means:

> I want my backend application to use and control the model.

# 2. Before running anything: understand the LLM

This section is intentionally written in simple language first, followed by the technical details. Understanding these concepts makes the rest of the project much easier to reason about.

## 2.1 What does 3B / 8B mean?

`3B`, `8B`, `14B`, etc. refer to the approximate number of **parameters** in the model.

They do **not** mean tokens.

A parameter is a learned numerical value inside the neural network.

For example:

```text
Llama 3.2 3B
       |
       +--> roughly 3 billion learned parameters
```

An 8B model similarly has roughly 8 billion parameters.

A useful mental model is:

```text
Parameters = the learned model weights
Tokens     = the pieces of text processed by the model
```

They are different things.

---

## 2.2 What is a token?

A token is a small piece of text produced by the model's tokenizer.

A token is not always equal to a word. Depending on the tokenizer, a token can be a whole word, part of a word, punctuation, or another small piece of text.

The high-level flow is:

```text
Your text
   |
   v
Tokenizer
   |
   v
Token IDs
   |
   v
LLM
   |
   v
Next-token probabilities
   |
   v
Generated tokens
   |
   v
Text
```

For a request, it helps to separate tokens into:

### Input tokens

Tokens you send to the model.

This can include:

```text
system instructions
conversation history
current user message
retrieved documents
tool results
```

### Output tokens

Tokens generated by the model.

### Total tokens

A simple usage view is:

```text
input tokens + output tokens = total token usage
```

With a local model there is no per-token API bill. Instead, token processing consumes your Mac's time, memory, bandwidth, battery, and power.

# 3. Parameters vs tokens vs context

These three terms are easy to mix up.

| Term | Meaning |
|---|---|
| Parameters | Learned numbers in the model |
| Token | A unit of text processed/generated |
| Context window | The amount of tokenized information the model can consider for a request |
| Input tokens | Tokens sent into the request |
| Output tokens | Tokens generated in the response |
| KV cache | Runtime memory used to keep attention state for processed context |

Think of it as:

```text
Model weights
    = the model itself

Tokens
    = the text going through the model

Context window
    = how much text can be considered at once
```

# 4. What actually happens when you ask a question?

Suppose you ask:

```text
Explain Redis caching in simple terms.
```

The model does not directly operate on the raw sentence. The request is tokenized and processed by the neural network.

A simplified view is:

```text
"Explain Redis caching..."
          |
          v
       Tokenizer
          |
          v
   [token1, token2, ...]
          |
          v
 Transformer layers
          |
          v
 Predict next token
          |
          v
 Predict next token
          |
          v
 Predict next token
          |
         ...
          |
          v
       Response
```

The important part is that generation happens **one token at a time**.

That is why streaming works: the gateway can forward chunks as the model produces them.

# 5. Quantization: why a large model can fit on a laptop

A model's parameters can be stored at different numerical precisions.

Very roughly:

```text
FP32  -> about 4 bytes per parameter
FP16  -> about 2 bytes per parameter
Q8    -> about 1 byte per parameter
Q4    -> about 0.5 byte per parameter
```

Real model files contain additional data and quantization overhead, so these are useful estimates rather than exact file sizes.

For an 8B model, a rough mental calculation is:

```text
8 billion parameters
x ~0.5 byte
------------------
~4 GB
```

A packaged Q4 model will normally be somewhat larger than that.

The trade-off is:

```text
More precision
    |
    +--> more memory
    +--> larger model
    +--> potentially better quality

Less precision / quantization
    |
    +--> less memory
    +--> smaller model
    +--> generally faster / easier to run locally
    +--> some quality loss
```

For a 16 GB Mac, Q4 models are a practical starting point for larger local models.

# 6. Why your M4 Mac is good for local LLMs

The Mac used for this project has **unified memory**.

Instead of thinking about separate CPU RAM and GPU VRAM, think about one shared pool:

```text
             16 GB Unified Memory
                    |
          +---------+---------+
          |                   |
         CPU                 GPU
```

That memory is shared with the rest of the operating system and applications.

So the model is competing for memory with things such as:

```text
macOS
VS Code
Chrome
Docker Desktop
Redis
Prometheus
Ollama
LLM weights
KV cache
```

This is why a model that is technically small enough to fit can still make the machine uncomfortable.

---

# 7. Why memory bandwidth matters

The M4 has roughly **120 GB/s memory bandwidth**.

For LLM decode, the chip repeatedly needs to move the model weights through memory. A useful intuition is:

```text
higher memory bandwidth
        +
smaller model
        =
usually higher generation speed
```

A simplified mental formula is:

```text
Decode speed ~ memory bandwidth / model size
```

It is not an exact benchmark equation, but it explains why quantized and smaller models can generate tokens faster.

The practical metric you will measure is:

```text
tokens / second
```

---

# 8. Prefill vs decode

This project measures two different parts of an LLM request.

## Prefill

The model processes the input prompt and existing context.

This is closely related to:

```text
TTFT = Time To First Token
```

If your prompt is large, prefill can take longer.

## Decode

The model generates the answer one token at a time.

This is where you usually watch:

```text
tok/s = generated tokens per second
```

So:

```text
Request
  |
  +--> Prefill ------> first token
  |                    |
  |                    +--> TTFT
  |
  +--> Decode -------> remaining tokens
                       |
                       +--> tokens/sec
```

This distinction is important when benchmarking.

---

# 9. KV cache: the hidden memory cost

Model weights are not the only thing using memory.

During generation, the transformer keeps attention information for tokens it has already processed. This is called the **KV cache** (Key/Value cache).

Conceptually:

```text
Token 1  -> KV information
Token 2  -> KV information
Token 3  -> KV information
Token 4  -> KV information
   ...
Token N  -> KV information
```

As the active context gets larger:

```text
more tokens
    |
    v
larger KV cache
    |
    v
more memory used
```

This is why context length can become the silent memory killer on a 16 GB machine.

Start with a smaller context such as:

```text
num_ctx = 4096
```

and increase it deliberately while watching memory pressure.

---

# 10. Why long conversations matter

Suppose a conversation contains:

```text
system prompt         200 tokens
turn 1                500 tokens
turn 2                700 tokens
turn 3                600 tokens
current question      300 tokens
--------------------------------
total                 2300 tokens
```

If the context limit is 4096, you still need room for the model's answer and runtime overhead.

Once the conversation grows too large, your service must decide what to do:

```text
keep recent messages
truncate older messages
summarize older messages
reduce retrieved documents
reduce tool output
```

The current project intentionally starts simple. Later versions can add an intelligent context builder.

---

# 11. Context length is not a token bank

If a model has a context window of 4096 tokens, that does **not** mean:

> You permanently have 4096 tokens and they get used up forever.

Context is per active request/conversation state.

For example:

```text
Request A -> 2000 tokens
Request B -> 1500 tokens
Request C -> 3000 tokens
```

does not permanently consume 6500 tokens from your machine.

The memory impact comes from the active requests and their runtime state.

---

# 12. Concurrency multiplies memory pressure

One request:

```text
1 model generation
1 context
1 KV cache
```

Four simultaneous requests:

```text
4 generations
4 active contexts
4 KV caches
```

This is why this project deliberately starts with:

```text
OLLAMA_NUM_PARALLEL=1
MAX_CONCURRENCY=1
MAX_QUEUE=2
```

The semaphore protects the laptop from being overwhelmed.

The mental model is:

```text
                 Incoming requests
                         |
               +---------+---------+
               |                   |
            RUNNING              QUEUE
               |                   |
               |             +-----+-----+
               |             |           |
             1 slot        wait         wait
               |
             Ollama
               |
          local LLM
```

When the queue is full, the gateway rejects additional work instead of allowing unlimited pressure to build.

# 13. Why the project uses a gateway at all

You can absolutely talk directly to Ollama:

```bash

```

You can also send an HTTP request directly to Ollama on:

```text
http://127.0.0.1:11434
```

That is useful when you simply want to use the model.

This project adds another layer because a real application needs concerns that are bigger than the model itself:

```text
Authentication
Rate limiting
Input validation
Concurrency control
Queueing / backpressure
Timeouts
Cancellation
Streaming
Metrics
Model allowlisting
```

So:

```text
Direct Ollama

Client -> Ollama -> Model
```

versus this project:

```text
Client
  -> Fastify Gateway
      -> Auth
      -> Rate limit
      -> Validation
      -> Queue / Semaphore
      -> Ollama
          -> Model
```

The gateway is the system you are learning to engineer.

Exposes health, readiness, and metrics endpoints.

`test/semaphore.test.ts`

Unit tests for queue/concurrency behavior.

`scripts/bench.ts`

Benchmarks TTFT, tokens/sec, total latency, and rejection behavior under concurrency.

Contains custom Ollama model configurations.

# 28. Why the gateway uses a semaphore

Your Mac has finite resources.

Suppose the gateway receives six requests while the model is configured for one active generation and a queue of two:

```text
Request 1 -> RUNNING
Request 2 -> QUEUED
Request 3 -> QUEUED
Request 4 -> REJECTED
Request 5 -> REJECTED
Request 6 -> REJECTED
```

This is admission control.

It prevents unlimited requests from reaching the LLM at once.

The implementation also releases the slot in a `finally` block so a failure or cancellation does not leak the slot.

# 31. Cancellation

Start a streaming request:

```bash
curl -N http://127.0.0.1:3000/v1/chat/completions \
  -H "authorization: Bearer $KEY" \
  -H 'content-type: application/json' \
  -d '{

    "stream":true,
    "messages":[{"role":"user","content":"Explain distributed systems in detail."}]

```

Press `Ctrl-C` while it is generating.

The gateway propagates cancellation through an `AbortController` and releases the concurrency slot.

This is important because the server should stop doing expensive work when the client has already gone away.

# 36. Important 16 GB Mac recommendations

### Start small

Use:

```text
3B-4B Q4
```

for comfortable development.

A 7B-9B Q4 model can also be practical with a moderate context, but you need to watch memory pressure.

12B-14B models are much tighter on 16 GB.

### Keep the context controlled

Start with:

```text
4096
```

and increase only after measuring.

### Keep one model loaded

```env
OLLAMA_MAX_LOADED_MODELS=1
```

### Keep concurrency conservative

Start with:

```env
OLLAMA_NUM_PARALLEL=1
MAX_CONCURRENCY=1
```

### Watch memory pressure

Use macOS Activity Monitor.

Yellow or red memory pressure is a warning that you are pushing the machine too hard and may be swapping.

### Remember the MacBook Air has no fan

Long benchmarks can cause thermal throttling. A result from the first few seconds is not necessarily the same as a sustained result over a long run.

# 38. OpenAI-compatible API design

The gateway exposes:

```text
GET  /v1/model
GET  /v1/models
POST /v1/chat/completions
```

`GET /v1/model` requires a bearer API key and returns only the configured
`DEFAULT_MODEL`:

```json
{ "id": "llama3.2:3b", "default": true }
```

`GET /v1/models` requires a bearer API key and returns the models configured in
`ALLOWED_MODELS`, marking `DEFAULT_MODEL`:

```json
{
  "data": [
    { "id": "llama3.2:3b", "default": true },
    { "id": "backend-mentor", "default": false }
  ]
}
```

This means an OpenAI-shaped client can be pointed at your local gateway by changing the base URL.

Conceptually:

```text
OpenAI SDK
    |
    v
http://127.0.0.1:3000/v1
    |
    v
Your gateway
    |
    v
Ollama
```

The important architectural idea is that your application talks to **your contract**, not directly to a specific model runtime.

That makes the model a swappable dependency.

## Stateful conversation API

Authenticated conversations are stored in PostgreSQL:

```text
POST   /v1/conversations
GET    /v1/conversations
GET    /v1/conversations/:id
PATCH  /v1/conversations/:id
DELETE /v1/conversations/:id
POST   /v1/conversations/:id/messages
POST   /v1/conversations/:id/forks
```

Fork at a message to create a new conversation with a snapshot of history through that message. The source is unchanged; the fork gets new message IDs and can use a different title or default model.

```http
POST /v1/conversations/{id}/forks
Authorization: Bearer <API_KEY>
Content-Type: application/json

{
  "fromMessageId": "<message-id>",
  "title": "Try another approach",
  "defaultModel": "optional-allowed-model"
}
```

Only user and assistant messages in the source conversation can be fork points. Omit `title` and `defaultModel` to derive the title and inherit the source model. The response is `201 Created`; it includes the new conversation's `parentConversationId` and `forkedFromMessageId`.

# 42. A useful interview explanation

A simple explanation is:

> I built a local LLM gateway around Ollama and Llama 3.2 3B on an Apple Silicon Mac. The gateway exposes an OpenAI-compatible API and adds API-key authentication, rate limiting, bounded concurrency, queue backpressure, request cancellation, streaming, and Prometheus metrics. I benchmarked TTFT and token generation speed under different concurrency settings and tuned the system for the memory constraints of a 16 GB unified-memory machine.

The interesting engineering problem is not just generating text. It is controlling a memory- and bandwidth-heavy workload while still exposing it as a reliable backend service.
